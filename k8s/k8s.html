生产级K8s基础设施层

跳过kubectl语法，聚焦"声明期望状态 → 调度决策 → 节点执行绑定"这条K8s最核心的调谐逻辑，以及围绕它的存储、网络、可观测性基建。

核心对象：地基层

对象作用
Pod最小调度单位，一个或多个共享网络/存储的容器
Deployment管理一组无状态、互相等价的Pod副本，滚动升级、故障自愈；不保证Pod间启动顺序和身份一致性
StatefulSet管理一组有稳定身份（固定序号、固定网络标识）的Pod，按顺序创建/销毁
Service给一组Pod一个稳定的虚拟IP/域名，做四层负载均衡
Ingress七层（HTTP/HTTPS）路由入口，按域名/路径转发流量
PV / PVCPersistentVolume是实际存储资源，PersistentVolumeClaim是Pod对存储的申请声明，两者解耦
StorageClass存储模板，定义PVC被创建时该怎么动态生成对应的PV

调度与资源模型

  • Scheduling Framework流水线：QueueSort → PreFilter → Filter → PostFilter → PreScore → Score → Reserve → Permit → PreBind → Bind → PostBind，Taint/Toleration、NodeAffinity在Filter阶段生效（淘汰候选节点），资源打分、拓扑打散在Score阶段生效（候选节点排序）
  • Requests/Limits 落地到cgroups：CPU Requests → cpu.shares（相对权重）；CPU Limits → cfs_quota_us/cfs_period_us（硬性限流）；Memory Limits → cgroup硬上限，超出直接OOMKilled
  • QoS三档（由Requests/Limits关系自动决定）：Guaranteed（两者相等）、Burstable（Requests<Limits）、BestEffort（都不设置），决定节点资源紧张时先驱逐谁
  • Taint三种effect：NoSchedule / PreferNoSchedule / NoExecute（连正在跑的Pod也会被驱逐，可配合tolerationSeconds设置容忍时长）
  • schedulerName：每个Pod可指定由谁调度，默认kube-scheduler，可指向Volcano、KAI Scheduler等——这是整个AI调度生态能够存在的入口开关，多个调度器通过Leader Election各自保证高可用，互不干扰

存储：CSI / PV / PVC

  • CSI是一套gRPC接口规范，分三个服务：Identity（自报身份能力）、Controller（卷创建/删除/扩容，通常以Deployment跑在管理面）、Node（实际挂载到节点，必须以DaemonSet跑）
  • Controller前面挂了一串社区通用sidecar：external-provisioner / external-attacher / external-resizer / external-snapshotter / node-driver-registrar
  • VolumeBindingMode：Immediate（PVC创建立刻绑定）vs WaitForFirstConsumer（等Pod调度到节点后才绑定）——大规模训练集群必须用后者，否则PV和Pod可能落在不同可用区导致死锁
  • AccessModes：ReadWriteOnce vs ReadWriteMany——多机共享的权重/数据集目录必须是RWX，对应并行文件系统（Lustre、CPFS、NFS），本地SSD做不到

网络：CNI / Service / Ingress / Gateway API

  • CNI两大流派：Overlay（VXLAN封装，如Flannel，有封装解封装开销）vs BGP路由/云厂商原生ENI（Calico BGP模式、VPC-CNI，Pod IP直接VPC可达，无封装开销）——AI训练场景优先选后者，避免拖慢跨节点AllReduce/HCCL通信
  • kube-proxy三种模式：iptables（链式遍历，O(n)）、ipvs（哈希查找，O(1)，大规模集群首选）、新版nftables
  • CoreDNS：集群内服务发现核心，Service名解析成ClusterIP靠它
  • Gateway API：Ingress的下一代替代，用GatewayClass/Gateway/HTTPRoute拆分基础设施团队和应用团队的职责边界，扩展点更细粒度
  • Multus CNI：meta-plugin，允许一个Pod挂多张网卡——管理流量走默认CNI，RDMA高速通信走第二张网卡直通SR-IOV/RoCE硬件

可观测性

  • Prometheus Operator引入的CRD：ServiceMonitor / PodMonitor（声明抓取目标）、PrometheusRule（告警规则）、Alertmanager CRD（告警路由）
  • 指标来源三层：cAdvisor（内嵌kubelet，容器级资源）、node-exporter（DaemonSet，宿主机级）、kube-state-metrics（K8s对象状态，与资源使用无关）
  • GPU/NPU指标不在上述任何一层，需额外部署 DCGM Exporter（NVIDIA）或 npu-exporter（昇腾）
  • 日志采集：Fluent Bit/Filebeat以DaemonSet逐节点tail /var/log/containers/ 再转发到Loki/ES

Pod调度与资源绑定全流程

决策（Scheduler）和执行（kubelet）分离；执行层四个接口都是可插拔标准，具体实现可按需替换。

易被忽略但重要的补充点

etcdK8s所有对象状态的唯一数据源，一致性键值存储；备份恢复策略和大规模集群下的写入延迟调优是生产最容易忽略但最致命的一环
Admission WebhookValidatingWebhook（校验）+ MutatingWebhook（改写，如自动给训练Pod注入RDMA设备声明）；平台自动化注入逻辑基本都靠这个实现
Reconcile Loop所有Operator共享的通用设计模式：持续对比期望状态与实际状态，有差异就调用原生API缩小差距，失败就重试
Topology Managerkubelet特性，协调CPU/Device/Memory Manager的分配决策落在同一NUMA节点，避免跨NUMA访问的延迟惩罚
Pod Disruption Budget声明一组Pod同时被主动中断的数量上限；没有PDB时集群升级可能同时重启训练组用到的多台节点，因Gang Scheduling强绑定直接团灭
Node Problem Detector检测节点硬件异常（GPU Xid错误等），发现后自动打Taint隔离故障节点，是故障自愈闭环里"发现问题"的一环

加速卡资源管理层

从Pod声明里的一个resources.limits字段，到真正绑定到一张物理GPU/NPU卡，中间的接口标准、组件生态与虚拟化机制。

Device Plugin：三段式gRPC交互

Device Plugin是跑在每节点的gRPC server，通过/var/lib/kubelet/device-plugins/下的Unix socket向kubelet注册：

  1. Registration：插件启动时向kubelet注册自己的资源名（如nvidia.com/gpu、huawei.com/Ascend910）
  2. ListAndWatch：长连接流式RPC，持续把本机可用设备列表推送给kubelet，更新节点的Capacity/Allocatable
  3. Allocate：Pod被调度到本节点且申请该资源时，kubelet调用它，插件返回该挂载哪些设备文件/环境变量
关键认知

Device Plugin本身不参与调度决策，只负责上报和挂载；具体怎么分配（比如优先分配拓扑相邻的卡）它管不了——这正是需要接入Volcano等次级调度器的原因。

GPU侧 vs NPU侧：组件对照

GPU侧（NVIDIA GPU Operator）NPU侧（华为 MindCluster / MindX DL）作用
NVIDIA Driver昇腾NPU驱动+固件硬件底层驱动
NVIDIA Container ToolkitAscend Docker Runtime本质是runC插件，让容器运行时能访问加速卡
Device PluginAscend Device Plugin把加速卡注册成K8s可调度资源
GPU Feature Discovery（节点标签检测）检测型号/特性，自动打节点标签
DCGM ExporterNPU-Exporter基于Prometheus/Telegraf暴露利用率、显存、温度等指标
MIG ManagervNPU虚拟化（静态/动态）卡内切分成多个虚拟实例
（原生无对应）Volcano NPU亲和性调度插件昇腾NPU存在卡间亲和性，需感知拓扑做高效调度分配

整套Operator走的是CRD+Operator模式：NVIDIA侧核心CRD是ClusterPolicy，声明要启用哪些能力，Operator据此在每个GPU节点拉起对应DaemonSet组件。

MIG / vNPU / Time-Slicing：切分≠切分

方案隔离级别说明
MIG硬件物理隔离切成最多7个独立实例，各自专属显存/计算核心/缓存；仅Ampere、Hopper等少数GPU支持
vNPU静态切分硬件物理隔离npu-smi命令直接创建/销毁，芯片层面硬切分
vNPU动态切分硬件物理隔离MindX DL自动创建，但每个Pod只能使用一张vNPU卡——与TP>1的大模型部署冲突
Time-Slicing / 软切分仅分时复用，无真隔离驱动层快速切换上下文，显存/算力没有硬隔离，一个容器打爆显存会影响同卡其他容器

左、中两种是芯片层面的物理切分，互不干扰；右侧Time-Slicing只是让多个容器"轮流用卡"，显存互相看得见、也互相打得爆。

Project-HAMi是跨厂商的开源方案，在原生Device Plugin基础上补上更细粒度的显存/算力配额能力，适合多租户细粒度算力售卖场景。

Topology Manager：NUMA对齐策略

none不对齐（默认，兼容性最好，性能最差）
best-effort尽量对齐，对不齐也放行
restricted必须对齐，对不齐拒绝调度——大规模训练建议至少用这个
single-numa-node最严格，所有资源须落在同一NUMA节点
生产坑点

MIG geometry变更是破坏性操作：变更期间device-plugin、gpu-feature-discovery、dcgm-exporter会被打上"paused-for-mig-change"暂停调度，须在低峰期操作。

vNPU"每Pod限一张卡"与TP>1冲突，所以GLM 5.2这类需要TP=8/16的大模型部署通常直接走整卡调度，不用vNPU。

昇腾NPU亲和性未配置好会拖慢多机训练，务必确认Volcano的NPU拓扑感知调度插件已启用。

训练侧编排

把超大MoE模型的分布式训练，从一堆手写脚本，变成K8s上声明式管理、能扛住节点故障的Job。

Kubeflow Trainer v2：三层职责分离

v1时代每种框架一个CRD（PyTorchJob、TFJob、MPIJob），v2统一成单一的TrainJob API，并把职责拆成三层：

角色使用的资源关心什么
平台管理员ClusterTrainingRuntime / TrainingRuntime预置基础设施模板：镜像、资源规格、分布式配置、调度策略
AI工程师TrainJob只填训练代码、节点数、资源量，引用一个现成的Runtime
K8s生态JobSet / Kueue / LWS在底层真正把Pod创建、torchrun启动、rendezvous配置这些"体力活"做掉

关键认知：TrainJob本身不直接管理Pod，它引用的Runtime底层封装的是JobSet（K8s原生的批量Job编排API）——这与Stage 4会讲到的LWS是同一批"Batch Working Group"孵化出来的姊妹API，一个面向训练的多Job编排，一个面向推理的多机部署。

# AI工程师只写这些，torchrun怎么启动、rendezvous怎么配，全部封装在Runtime里
apiVersion: trainer.kubeflow.org/v1alpha1
kind: TrainJob
metadata:
  name: glm52-finetune
spec:
  runtimeRef:
    kind: ClusterTrainingRuntime
    name: torch-distributed
  trainer:
    numNodes: 8
    resourcesPerNode:
      limits:
        huawei.com/ascend-910: 8

Gang Scheduling：三条技术路线怎么选

当资源不足以调度任务所需的全部Pod时，默认调度器会让所有Pod停在Pending状态互相等待——MoE大模型训练最容易踩这个坑：几十个Pod里卡住两三个，整个任务假死。三条主流路线原理并不相同：

方案核心对象"All-or-Nothing"怎么实现
VolcanoPodGroupPod携带PodGroup引用，调度器只有在能凑齐minMember个Pod的资源时才批量放行，凑不齐全部退回队列
KueueWorkload把一个Job的所有Pod包成一个Workload对象，在Pod真正被创建前先在准入层排队，直到ClusterQueue能保证全部资源到位才放行——从源头上不给partial scheduling机会
KAI SchedulerPodGroup（NVIDIA实现）思路与Volcano类似，专为GPU场景做了拓扑感知与Pod重调度优化
CoschedulingScheduler Plugins的PodGroup作为kube-scheduler的插件运行，轻量，不需要单独部署一套调度器

Kueue的资源管理模型值得单独记一下，因为它同时解决了gang scheduling和多租户配额两个问题：

  • ResourceFlavor：定义集群里有哪些"资源口味"（比如带InfiniBand的GPU节点 vs 普通节点）
  • ClusterQueue：定义配额和公平共享规则，支持配额借用——团队A闲时，团队B可以临时借用A的额度，资源紧张时自动收回
  • LocalQueue：命名空间级的用户入口，指向某个ClusterQueue
  • Workload：Kueue对"一个Job的Pod组"的抽象，只有当ClusterQueue能同时满足这个Workload全部资源需求时才会被准入（QuotaReserved状态）
选型建议

昇腾生态优先Volcano（官方MindCluster生态深度集成，NPU亲和性调度也靠它）；GPU多租户配额+跨集群调度优先Kueue；只是想给已有kube-scheduler加一个轻量gang scheduling能力、不想引入独立调度器，选Coscheduling。

同样8个Pod，无gang scheduling时"抢到资源的先跑"，有gang scheduling时要么全员就绪、要么全员等待。

弹性容错：TorchElastic怎么做到"挂一个节点不死全部"

PyTorch弹性训练（TorchElastic / PET）的核心是给每个节点配一个elastic-agent常驻进程，它不直接跑训练代码，而是管理本节点上的worker进程并和其他节点的agent做成员协商：

  1. 某个worker进程失败时，本节点的elastic-agent会杀掉本节点上全部worker（不只是失败的那个）
  2. 存活的agent之间重新做一次rendezvous（基于etcd的集合点，协商新的participant列表、RANK、WORLD_SIZE）
  3. 用新的成员信息重启worker，训练从上一个已知良好状态恢复
容易理解错的一点

TorchElastic不负责checkpoint的保存与加载——这部分被有意设计成"bare-bones"，必须由训练脚本自己实现torch.save / torch.load并写到RWX共享存储（对应Stage 1讲的CSI持久卷）。elastic-agent只负责进程编排和rendezvous，真正的状态恢复逻辑是用户代码的责任。

K8s上对应的是ElasticJob CRD（elastic.pytorch.org/v1alpha1），声明minReplicas/maxReplicas区间而非固定副本数，配合Spot/竞价实例可以做到"资源紧张时缩容、资源充裕时扩容"而不用重启整个训练任务。这与Kubeflow Trainer v2里的PodFailurePolicy是互补关系：后者决定Pod失败后K8s层面要不要重建/算不算Job失败，前者决定训练进程层面怎么重新组织幸存的worker。

推理侧编排

多机PD分离的推理服务，传统Deployment/StatefulSet已经不够用，这是这两年变化最快的一层。

为什么Deployment/StatefulSet都不够用

Deployment的Pod彼此等价、互不感知身份，无法表达"这几个Pod共同组成一个推理实例"这种关系；StatefulSet虽然有身份和顺序，但它管理的是一组同构的独立个体，而多机推理需要的是"1个Leader（负责调度请求、聚合输出）+ N个Worker（分摊TP/PP权重）"这种异构但绑定为一个整体的拓扑——这正是LWS要解决的问题。

LeaderWorkerSet：控制器怎么把"组"翻译成K8s原生对象

LWS本身是CRD+Operator，底层仍然落地为StatefulSet——可以理解成在StatefulSet之上包了一层"组管理"：一个LWS副本 = 1个Leader StatefulSet（size=1）+ 1个Worker StatefulSet（size=N-1），LWS控制器负责让这两者的生命周期保持同步。两个关键配置：

字段作用
spec.startupPolicyLeaderCreated（默认，Leader Pod一创建就立刻建Worker，不保证就绪顺序）vs LeaderReady（延迟到Leader Ready后才创建Worker StatefulSet）
leaderworkerset.sigs.k8s.io/exclusive-topology注解声明LWS副本与某个拓扑域（如机架）的1:1绑定关系，确保一个推理实例内的多机始终调度到同一机架，保证跨节点通信效率

size字段直接对应你要部署的TP/PP并行度——比如GLM 5.2需要8卡×2机做TP=16时，size: 2就是Stage 5示例里那个manifest的由来。

PD分离：llm-d的组件拆解

PD分离要解决的根本问题：prefill阶段并行处理整个prompt，是计算密集型；decode阶段每步只算一个token但要读取全部KV cache，是显存带宽密集型——两者混部在同一实例上时，一个长prefill请求会阻塞正在解码的请求（head-of-line blocking）。llm-d把这套编排标准化为几个组件：

组件作用
Inference Gateway (IGW)基于Gateway API构建的代理层（如kgateway），是请求的统一入口
llm-d SchedulerKV cache感知路由：跟踪每个decode worker持有哪些KV cache块，命中相同前缀的请求会被路由到已缓存该前缀的worker上，最大化前缀缓存命中率
Decode端sidecar协调prefill worker和decode worker之间点对点的KV cache传输，通过NVLink/InfiniBand等高速互联搬运，让decode worker能拿到必要的上下文

它是CNCF在2026年接受的sandbox项目，由IBM Research、Google、Red Hat、CoreWeave和NVIDIA共同构建，目标是把K8s变成生产级LLM推理平台。与NVIDIA Dynamo的关键区别：Dynamo是跑在K8s之外的编排层，用NIXL做KV cache传输，深度绑定NVIDIA自家硬件栈；llm-d则完全用标准K8s原生对象（CRD、Gateway API），如果团队本来就在自建K8s集群、不想引入一套独立的专有控制面，llm-d是更自然的路径。

Selective PD：不是所有请求都值得拆

llm-d的inference-scheduler内置了pd-profile-handler插件（默认关闭）：当prompt足够短、"拆成prefill+decode两阶段再做一次KV传输"的开销反而超过"直接在同一个decode worker上把两阶段都做完"时，调度器会选择跳过分离、直接走decode-only路径——PD分离不是无脑全量启用的开关，而是要按请求特征动态决策的一层策略。

EPP决定请求先去哪个Prefill worker、再由哪个Decode worker接手——KV Cache的点对点传输是两者之间唯一的强耦合。

推理网关：Gateway API Inference Extension

在Stage 1讲过的Gateway API基础上，这个扩展新增了两个关键CRD，分工对应两种角色：

CRD面向角色作用
InferencePool平台管理员定义一组共享同样计算配置、加速卡型号、基础模型、模型服务框架的Pod，类似"专为推理设计的Service"
InferenceObjective（原InferenceModel）AI/ML负责人把一个公开模型名映射到InferencePool内的具体版本，支持流量按权重切分（用于A/B测试或灰度）、设置请求优先级

请求处理流程：Gateway根据HTTPRoute先匹配到目标InferencePool，再把请求转发给绑定的Endpoint Picker（EPP）——EPP持续跟踪每个模型服务器的KV cache利用率、排队长度、活跃LoRA适配器等指标，据此决定最终路由到哪个具体Pod，再通过响应头把选中的endpoint告知代理层。这一整套（代理+EPP）合起来才构成完整的"Inference Gateway"。

自动扩缩容：HPA vs KEDA

核心认知：不要用CPU/GPU利用率做推理扩缩容的信号。vLLM靠PagedAttention把GPU利用率维持得很高，一个85%利用率的Pod可能在从容处理5个请求，也可能在吃力支撑500个——利用率数字本身分辨不出Pod是否过载。真正该看的是请求级指标：

vllm:num_requests_waiting排队等待处理的请求数——最常用的扩容信号
vllm:gpu_cache_usage_percKV cache利用率
vllm:time_per_output_token_secondsTPOT，解码阶段的每token延迟
vllm:e2e_request_latency_seconds端到端请求延迟

HPA原生只能接CPU/内存或需要额外部署Prometheus Adapter才能接自定义指标；KEDA内置Prometheus scaler，直接查询PromQL作为触发器，背后仍然是生成并托管一个标准HPA对象（kubectl get hpa能看到`keda-hpa-xxx`），因此不冲突、是KEDA在HPA之上做的能力扩展而非替代。KEDA还额外提供Scale-to-Zero（空闲彻底缩到0实例）和多触发器组合（比如同时接排队长度和DCGM的GPU利用率，前者防止过载、后者提前预热应对突发流量）。

生产坑点

扩容的瓶颈往往不是KEDA配置本身，而是模型加载耗时——一个几百GB的MoE模型从存储加载到显存可能要数分钟，扩容信号触发到新Pod真正Ready之间有明显延迟。对策是提前用PVC/共享存储缓存好模型权重，并给scaleUp设置合理的stabilization window避免抖动，scaleDown则应该更保守（比如300秒稳定窗口、每次只减1个副本）。

05已深入讲解

实战贯穿：GLM 5.2生产化部署

把前四个阶段串起来，落到一次真实的部署方案设计上——这里能看到Stage 1-4的每一层是怎么互相咬合的。

模型规格与硬件选型

GLM-5系列是78层decoder-only架构，前3层Dense FFN、后75层MoE（路由专家+共享专家），自带一层MTP用于加速解码；GLM 5.2在此基础上扩展到753B参数规模。

量化路线硬件需求
BF162台Atlas 800 A3（128G×8）或 4台Atlas 800 A2（64G×8）
W8A8量化1台Atlas 800 A3（128G×8）或 2台Atlas 800 A2（64G×8）
FP8（GPU路线）约750GB权重，8×H200单节点1.13TB HBM可容纳权重+KV cache

硬件路线直接决定了Stage 2讲的加速卡资源管理策略：TP≥8的部署必须走整卡调度（vNPU"每Pod限一张卡"的限制在这里生效），且NUMA对齐建议至少用restricted策略，避免CPU预处理和NPU之间跨NUMA搬运数据拖慢首字延迟。

为什么必须做PD分离，而不是一个LWS通吃

GLM 5.2这类超大MoE模型的prefill阶段要对1M上下文做全量attention计算，是重度计算密集型；decode阶段虽然每步只算一个token，但753B参数+超长KV cache的读取是显存带宽密集型。两者混部在同一组实例上，一个长文档的prefill请求会直接阻塞正在解码的会话——这正是Stage 4讲的head-of-line blocking，在GLM 5.2的1M上下文场景下会被放大到极致。因此生产部署必须把prefill和decode拆成两个独立的LWS：

用LWS建模GLM 5.2的多机拓扑

把prefill和decode拆成两个独立的LWS，是PD分离在K8s上的落地方式——重点不是记语法，而是理解为什么要拆：prefill计算密集、decode显存带宽密集，扩缩容特性完全不同。

Prefill池容量偏静态，Decode池挂自动扩缩容——两个LWS各自独立伸缩，互不牵连。

  annotations:

spec:
  replicas: 1
  startupPolicy: LeaderReady  # Leader就绪后才拉起Worker，避免脑裂
  leaderWorkerTemplate:
    size: 2  # 对应手写脚本里的 node0/node1
    leaderTemplate:
      spec:
        containers:
        - name: vllm-ascend-leader

          env:
          - name: HCCL_SOCKET_IFNAME
            value: "<按拓扑标签动态注入>"
          resources:
            limits:
              huawei.com/ascend-910: 8
    workerTemplate:
      spec:
        containers:
        - name: vllm-ascend-worker
          image: quay.io/ascend/vllm-ascend:glm5.2-a3
          resources:
            limits:
              huawei.com/ascend-910: 8

两个LWS部署好之后，还需要Stage 4讲的两个组件把它们真正接入生产流量：一是分别给prefill池和decode池建InferencePool，由llm-d Scheduler做KV cache感知路由和Selective PD决策；二是给decode池挂一个KEDA ScaledObject，用vllm:num_requests_waiting做扩缩容触发器——prefill池通常不需要这么激进的自动扩缩容，因为它的负载模式更接近批处理，容量规划可以偏静态。

06已深入讲解

生产化收尾

补齐从"能跑起来"到"能稳定运维"之间的最后一段距离——这一层几乎全部是Stage 1可观测性基建和Stage 4推理编排的组合应用。

监控指标接入

vLLM/vLLM-Ascend原生暴露Prometheus格式指标，配合Stage 1讲的ServiceMonitor即可自动被抓取，Grafana侧重点看这几类：

TTFT（首字延迟）直接反映prefill阶段排队与计算耗时，是用户感知到的"响应速度"
TPOT（每token延迟）反映decode阶段的显存带宽压力，超长上下文场景下最容易劣化
KV cache命中率llm-d Scheduler路由质量的直接体现，命中率低说明前缀缓存没发挥作用
num_requests_waitingStage 4讲过的核心扩容信号，也是判断"该扩容还是该拒绝新请求"的依据

灰度发布：金丝雀验证量化策略切换

比如要把decode池从W8A8切到W4A8量化，直接全量切换风险很高——量化精度损失对长尾请求的影响很难靠离线评测完全覆盖。生产上通常用Argo Rollouts或Flagger这类渐进式发布控制器，配合Gateway API的流量权重能力做金丝雀：

  1. 先用InferenceObjective的targetModels权重字段，把小比例（如5%）流量导向新量化版本的Pod
  2. 用Stage 6上面这套监控指标（尤其是TPOT和错误率）做自动化的金丝雀分析，对比新旧版本表现
  3. 指标健康则逐步调大权重（5%→25%→50%→100%），指标劣化则自动回滚权重到0——这个"渐进+自动回滚"的逻辑正是Argo Rollouts/Flagger相比手动改Deployment权重的核心价值

柱子中的青色部分是新量化版本（如W4A8）承接的流量占比，灰色是旧版本；每一步放量前都要过一次指标门禁。

和Stage 1的PDB要配合

灰度过程中新旧版本Pod同时存在，如果这时候又赶上集群节点维护触发滚动重启，PDB能防止某一版本的Pod被一次性全部驱逐——灰度发布和故障自愈两件事看似无关，但都依赖同一个PDB机制兜底。

跨云场景的存储与网络对接

如果训练在阿里云、推理部署在华为云（对应你之前做过的CPFS→OBS跨云迁移背景），这一层要提前规划好：

  • 模型产物怎么过去：训练产出的Checkpoint/最终权重需要一条稳定的跨云同步链路，落到Stage 1讲的CSI持久卷上，供推理侧LWS的Pod挂载
  • 两套监控体系怎么合并：阿里云和华为云各自的Prometheus/Grafana实例，如果需要统一大盘，要么用Thanos/VictoriaMetrics做跨集群联邦查询，要么在两边分别配置远程写入到统一的时序库
  • 跨云延迟对PD分离的影响：如果prefill和decode被迫跨云部署（不建议，但某些容灾场景会这样设计），KV cache传输的跨云网络延迟会显著抵消PD分离带来的收益，这时候pd-profile-handler的阈值需要重新评估
