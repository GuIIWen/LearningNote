# Model Context Protocol (MCP) - 智能 Agent 设计模式

## 1. 核心理念与本质
### 什么是 MCP？
- **通用标准接口**：一个开放协议，旨在标准化 LLM（如 Gemini, Claude）与外部数据源、工具、应用程序的通信方式。
- **系统解耦**：允许任何兼容的 LLM 连接到任何符合 MCP 标准的外部系统，无需为每个数据源编写自定义集成代码（避免“造轮子”）。
### 架构设计
- **客户端-服务器模型 (C/S 架构)**
  - **MCP 客户端**：发起请求的一方（如 LLM 宿主应用或 AI Agent）。
  - **MCP 服务器**：提供外部能力的一方，公开特定领域的资源或功能。

## 2. 核心三大要素 (MCP Server 暴露的元素)
### 资源 (Resources)
- **定义**：静态数据或信息。
- **应用**：例如，暴露给 Agent 的波音装配手册 PDF，或者内部图数据库中的只读节点数据。
### 模板 (Prompts / Templates)
- **定义**：预置的交互模板或提示词框架。
- **应用**：辅助 Agent 以标准化的方式获取特定业务领域的上下文。
### 工具 (Tools / Functions)
- **定义**：可执行的、带有确定性输出的函数操作。
- **应用**：例如，触发 Salesforce 数据同步的脚本、调用物流排程的外部算法。

## 3. MCP 与传统函数调用 (Tool Function Calling) 的本质区别
### 抽象层级
- **函数调用 (Function Calling)**：特定 LLM 和特定定制工具之间的**一对一**直接请求（专有、与供应商绑定紧密）。
- **MCP**：标准化通信框架，支持生态系统级的**多对多**互操作。
### 发现机制 (Discovery)
- **函数调用**：开发者必须在 Prompt 中明确“硬编码”告诉 LLM 有哪些工具可用。
- **MCP**：支持动态发现。客户端 Agent 可以查询 MCP 服务器：“你现在能提供什么能力？”
### 企业资产盘活 (遗留系统集成)
- **函数调用**：往往需要重写旧系统以适配当前的大模型。
- **MCP**：通过给旧系统套一层“符合 MCP 接口的 Wrapper (包装器)”，让旧服务免修改即刻接入现代 AI 编排流。

## 4. MCP 在工程落地中的关键考量
### 接口的设计粒度 (API Design)
- **反面教材**：粗暴封装一个只支持全量数据拉取的低效遗留 API。
- **最佳实践**：必须在 MCP 接口层提供**确定性的过滤、排序和分页机制**，以防非确定性的 Agent 因数据过载而崩溃或变慢。
### 数据格式对齐 (Data Format Compatibility)
- Agent 看不懂复杂的二进制或封闭格式。MCP 必须将数据转译为 Agent 友好的格式（如将 PDF 转为 Markdown 文本结构），否则连接毫无意义。

## 5. 开发与部署框架
### FastMCP
- 高级 Python 框架，极大简化了 MCP 服务器的开发。
- 核心优势：通过 `@mcp_server.tool` 装饰器，利用 Python 函数的**签名、类型提示和文档字符串 (Docstrings)** 自动生成标准的模型接口规范（Schema），杜绝手动编写 JSON Schema 的错误。
### 本地与网络通信 (Transports)
- **Stdio (标准输入输出)**：通过 `npx` 或 `uvx` 直接在本地进程间快速调用（如本地文件系统操作）。
- **HTTP / SSE**：分布式部署，Agent (客户端) 和 MCP Server (服务端) 通过网络进行远程调用。
